# 0049 Windows 本地 Git 仓库使用原生文件监听

- 状态：已采用（2026-11）；替代 [0003](0003-file-watching.md) 的 Windows 本地 Git 轮询策略。

## 背景

大型工作树即使完全空闲，原先也每 30 秒执行一次完整状态查询。外部编辑在两次轮询之间发生时，界面可能等待同样长的时间。见 [#4](https://github.com/muchenhen/viff/issues/4)。

## 替代项

- 延长所有仓库的轮询间隔：降低空闲负载，但外部编辑和 Git 操作的状态延迟也会增加。
- 按生成目录名硬编码排除：目录里可能有强制跟踪的文件，同名目录也可能适用不同规则。
- 使用 Git fsmonitor 或第三方监听库：前者依赖 Git 版本和仓库配置，并不为 Viff 提供刷新通知；后者增加依赖。现有 `golang.org/x/sys/windows` 已覆盖所需 Win32 接口。

## 决定

- 本地固定磁盘的 NTFS/ReFS Git 仓库用 `ReadDirectoryChangesW` 订阅工作树、实际 Git 元数据目录和 common dir。按解析后的卷及目录身份去重，重叠目录只订阅一次；普通仓库通常一个订阅，独立的 linked worktree 通常两个。子目录由 Windows 递归监听，Viff 不遍历 junction 或符号链接目标，也不会按文件创建句柄。
- 保留 HEAD、index、引用、配置和进行中操作的通知，过滤 Git 对象、LFS 对象缓存、reflog 及临时锁。普通路径按批使用 Git 的忽略规则和索引判断；整批被忽略时再用不区分 ASCII 大小写的字面路径规范核对索引。歧义路径和失败的判断会触发刷新。
- 每个订阅使用一个 64 KiB 缓冲；一批最多 256 个不同路径和 16 KiB 路径文本，只有一个判断在执行和一批待处理。首批合并 250 毫秒，持续事件至多每秒开始处理一批。内核丢失或超过应用上限时，丢弃待处理路径，在事件安静 750 毫秒后校验状态和属性发现，最长等八秒。应用侧也只保留一个待处理刷新，并让应用内写操作结束时的查询覆盖此前已观察到的事件。
- 健康监听每五分钟校验一次 Git 状态；从其他应用返回 Viff 时在下一次前台采样中校验，睡眠恢复时也重新校验。目录被移走、替换或监听中断时重新打开，失败期间每五秒检查元数据、每 30 秒兜底查询工作树，重试退避上限为 30 秒。
- UNC、网络映射盘、其他文件系统和 SVN 继续轮询，WSL 保持五秒轮询，SSH/macOS/Linux 策略保持原样。关闭或切换取消监听和旧状态查询；回调按打开代次校验。Git 仍是状态的来源。

## 代价

持续解包或生成资源仍可能超过缓冲上限，需要完整校验；通常由一轮在途状态查询和一个待处理请求吸收。短暂的焦点切换可能发生在两次采样之间，常规文件事件和周期校验仍在运行。对位于监听树以外的 reparse point 目标内容，周期校验提供兜底。

## 复审条件

- 发现 Windows 本地仓库稳定空闲五分钟内超过一次工作树兜底查询，或可复现的普通外部修改需要等到兜底才更新时，重跑 [平台验收](../testing.md#windows-native-file-watching--windows-原生文件监听)。
- 真实大型仓库里出现持续溢出、忽略路径核对开销明显或反复重连时，先比较状态查询次数、CPU 和句柄数，再调整批大小、恢复策略或路径核对方式。
